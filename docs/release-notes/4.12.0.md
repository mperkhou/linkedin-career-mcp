# 4.12.0 - Add scoped Codex manual-pass profiles

Version 4.12.0 separates manual-pass execution quality choices from the
independent resume-highlighting configuration. Operators can choose an
allowlisted manual profile in the Flask tracker or Make workflow without
changing process-wide state or allowing browser-provided model strings.

## Profile Defaults

Manual pass supports exactly three profiles:

| Profile | Model | Reasoning effort |
| --- | --- | --- |
| `economy` | `gpt-5.6-terra` | `high` |
| `regular` (default) | `gpt-5.6-sol` | `high` |
| `premium` | `gpt-5.6-sol` | `xhigh` |

Highlighting remains independently fixed by default at
`gpt-5.6-luna`/`high`. A manual profile is attached only to manual-pass
commands and never controls v1, v2, or highlighting.

## Tracker Behavior

The Actions menu retains one `Run v1 + v2 + Codex Manual Pass` mode and also
supports the standalone manual action. Its compact native profile selector is
hidden and disabled until either manual mode is active; Actions initially has no
selected mode.

The Add Seed, LinkedIn URL, and Other URL workflows expose the same selector
only while manual pass is enabled. Seed initially selects v1 and v2 with manual
pass off. The URL forms initially select highlighting while v2 and manual pass
are off. Manual pass requires v2, so clearing v2 disables and unchecks manual
pass and hides and disables the selector. The three displayed choices are:

- `Economy — Terra / High`
- `Regular — Sol / High (Recommended)`
- `Premium — Sol / X-High`

Only the allowlisted profile key is submitted. A missing key resolves
server-side to `regular` for older or JavaScript-free requests. An invalid key
rejects the request before a background action starts. The choice then travels
immutably through request parsing, background-thread arguments, the workflow
stage, and the manual Make command, allowing concurrent runs to use different
profiles without cross-run leakage.

## Overrides and Compatibility

Profile selection resolves from an explicit script option or
`MANUAL_PASS_PROFILE`, then
`LINKEDIN_CAREER_MCP_MANUAL_PASS_PROFILE`, then `regular`.

Model and reasoning effort are presence-aware and resolve independently:

1. Direct script option or workflow-specific Make override:
   `MANUAL_PASS_CODEX_MODEL`/`MANUAL_PASS_CODEX_REASONING_EFFORT` or
   `HIGHLIGHT_CODEX_MODEL`/`HIGHLIGHT_CODEX_REASONING_EFFORT`.
2. Matching workflow-specific `LINKEDIN_CAREER_MCP_*` environment value.
3. Deprecated shared Make fallback `CODEX_MODEL` or
   `CODEX_REASONING_EFFORT`.
4. Deprecated shared script fallback `LINKEDIN_CAREER_MCP_CODEX_MODEL` or
   `LINKEDIN_CAREER_MCP_CODEX_REASONING_EFFORT`.
5. Selected manual profile or fixed highlighting default.

An explicitly empty reasoning effort inherits the Codex CLI configuration.
Shared command, timeout, and retry controls remain supported and are not part of
the deprecated model/effort pair. Legacy shared model and effort overrides
remain available as compatibility fallbacks, but new operator configuration
should use the workflow-specific settings.

## Metadata, Provenance, and Variant Semantics

Manual-pass metadata records the selected profile together with the resolved
Codex client, model, reasoning effort, and command. Highlighting preserves the
target variant's source, parent, evidence, critique, validation, artifact, and
generation/manual metadata, then records its own client, model, effort, and
command separately under nested `highlighting` metadata.

Profiles do not create additional variant keys. Every manual run upserts the
same `(job_id, "manual")` row, so rerunning with another profile replaces that
job's one manual variant while retaining `v1` and `v2`. Explicit Review-page
selections remain untouched; rows in automatic-selection mode continue to
prefer `manual`, then `v2`, then `v1`. Highlighting updates its intended
existing target (`manual` after a chained manual pass, `v2` after v2-only
refinement, or the selected/default variant otherwise).

## Migration and Evaluation Notes

No database migration is required. Existing application rows and DB-backed
resume variants remain valid and unchanged until a workflow is rerun.

In v4.11 and earlier, unset workflow-specific configuration fell back to the
shared `gpt-5.5`/`xhigh` default for both manual pass and highlighting. With
shared overrides unset in v4.12.0, manual pass now uses the `regular`
`gpt-5.6-sol`/`high` profile and highlighting uses its separate
`gpt-5.6-luna`/`high` default. Existing explicit shared overrides continue to
work as deprecated fallbacks; unset or replace them to adopt the split defaults.

Comparative model-quality runs across economy, regular, and premium have not yet
been performed. `Regular` is the configured recommended default, not a
benchmark-derived winner; this release validates configuration, isolation,
provenance, and workflow integration rather than output-quality ranking.
