# 4.0.0 Release Notes: DB-Backed Second-Pass Resume Variants

Version 4.0.0 changes resume refinement from an overwrite-oriented workflow into
a versioned review workflow. The first draft remains available as `v1`; the GLM
second pass writes `v2`; and Codex manual review writes a separate `manual`
variant. The active resume links in the tracker are just the selected variant and
can be switched back and forth.

## Why This Release Exists

The first-draft ARO generator is now good enough to use as a reliable baseline,
but second-pass critique still needs evidence discipline. A model can improve
fit by reordering material, tightening language, and surfacing supported
aliases, but it can also overreach by adding unsupported skills, tools, metrics,
or responsibilities.

The release separates generation from selection:

- Always preserve the first draft.
- Store the second-pass output and its critique trail in SQLite.
- Let the user compare v1, v2, and manual variants before choosing which resume
  links to use.
- Make variant selection reversible.

  weighted terms, noisy phrase matches, component scores, and formatting signals.

- Added patch validation that rejects unsupported skills, tools, metrics,

- Added external critique ingestion that classifies suggestions as `supported`,

## How the GLM 5.2 V2 Pass Works

The v2 pass is a critique-and-validation workflow, not an unrestricted rewrite.
After v1 exists, `make refine-draft-resumes` builds an evidence packet and sends
GLM 5.2 a prompt with:

- job identity: job id, company, and title
- the current v1 ARO content being reviewed
- JOD target evidence extracted from the posting
- source evidence from the MRO and rendered ARO bullets
- ATS diagnostics, including score, matched terms, missing weighted terms, and
  noisy phrase evidence
- optional externally pasted critique, but only suggestions already classified
  as `supported`

The prompt tells GLM 5.2 to return only JSON and to propose small,
evidence-backed improvements. It explicitly tells the model not to apply
changes and not to add a skill, metric, employer, tool, domain, compliance
claim, credential, or responsibility unless the payload evidence directly
supports it. ATS noisy phrases are diagnostic context, not text to copy into the
resume.

The expected response is shaped like this:

```json
{
  "schema_version": "second_pass_resume_critique.v1",
  "proposed_changes": [
    {
      "change_id": "supported-observability",
      "change_type": "rewrite_bullet",
      "target": {
        "section": "professional_experience",
        "field": "text",
        "job_order": "1",
        "bullet_order": "2"
      },
      "current_text": "Existing bullet text.",
      "proposed_text": "Evidence-backed replacement text.",
      "rationale": "Why this improves role alignment.",
      "evidence_refs": ["mro:job:1:bullet:2", "jod:target:1"],
      "unsupported_claims": []
    }
  ]
}
```

The validator then decides what actually becomes v2. A recommendation is
accepted only when it cites known evidence refs, targets a real ARO field, its
`current_text` still matches the v1 ARO, and the proposed text does not
introduce unsupported factual terms. Accepted recommendations are applied to a
deep copy of v1 and rendered as the `v2` variant.

Rejected recommendations are stored but not applied. For example, if GLM
suggests adding "Kubernetes platform ownership" or "SOC 2 compliance leadership"
and those claims are not present in the MRO/ARO evidence, the recommendation is
rejected with validation issues such as `unsupported_claims_declared`,
`unknown_evidence_refs`, or `unsupported_factual_terms`. The tracker review page
can show those rejected recommendations, but the final resume remains truthful
to the existing experience and skills unless the user later adds real evidence.

For auditability, the `v2` variant stores the critique prompt, raw GLM response,
parsed critique JSON, accepted and rejected patch report, ATS diagnostics before
and after refinement, optional external critique classification, evidence
packet, and model metadata.

## Evidence Rules

Second-pass refinement can improve presentation, but it cannot invent facts.
Accepted changes must be grounded in the existing MRO/ARO evidence. Supported
operations include rewording, reordering, emphasis, and supported aliases for
skills already present in evidence. Rejected operations include adding new
skills, tools, employers, metrics, compliance claims, or responsibilities that
are not already supported.

ATS missing terms are review signals. They can help identify alignment gaps, but
they are not instructions to stuff keywords into the resume. If a missing term
is unsupported by master-resume evidence, it should remain rejected or be marked
as needing user evidence.

## Migration Notes

- Existing ARO rows are backfilled into `application_resume_variants` as `v1`
  when the database is opened through the webapp/schema migration path.
- Running `make regenerate-resumes JOB_IDS=all` creates or refreshes v1 drafts,
  then stores `v2` rows for active postings without changing the selected resume
  variant.
- Running `make regenerate-draft-resumes JOB_IDS="<job_id>"` remains available
  when only the v1 draft should be created or refreshed.
- Running `make refine-draft-resumes JOB_IDS="<job_id>"` creates v2 when it is
  missing or reruns and replaces v2 when it already exists.
- The selected variant is stored on the application row and controls the normal
  tracker resume HTML/PDF links. Selecting v2 or manual does not delete v1.
- Manual pass generation is intentionally per-job. Use
  `make manual-pass-resumes JOB_IDS="<job_id>"` or the tracker action after
  v1/v2 context exists.

## Validation

The implementation is covered by focused tests for ATS diagnostics, noisy phrase
regressions, critique parsing, external critique classification, patch
validation, Makefile targets, DB variant storage, reversible Flask selection, and
manual pass variant storage.
