# 5.0.0 Plan: Public Rebuild Workspace Separation

Status: planned

Target release: `5.0.0` in the existing private
`mperkhou/linkedin-career-mcp` repository

Eventual public baseline: a history-free `1.0.0` repository created in a later
release

## Objective

Create a private parallel implementation copy of the known-working LinkedIn
Career MCP application and separate its operational state from its code
checkout without changing resume-generation behavior. The parallel copy is a
release-candidate workspace; it does not replace the existing project
repository or operational checkout.

Phase 1 ends only after the implementation branch has been pushed to and merged
in the existing private project repository, this operational checkout has been
fast-forwarded to clean `main`, and the live Flask application has operated
successfully against the external private workspace. Final acceptance requires
the user's explicit confirmation after using the app for normal job-application
work.

This plan covers workspace separation only. Synthetic data replacement, live
synthetic generation, documentation replacement, privacy auditing, public
repository creation, public-clone cutover, and project renaming remain future
work in the rolling
[5.1.0 roadmap](5.1.0-public-rebuild-roadmap.md).

## Execution Model

- The planning task that approves and maintains this document is the
  supervisor. This tracked Markdown plan is the workflow source of truth; do
  not initialize or use the legacy runtime workflow tracker.
- The supervisor dispatches exactly one bounded `Pnn` step at a time to one
  separate user-owned implementor task. Every launch, later P-step prompt, and
  correction requires an exact preview and fresh approval except for the one
  narrowly restorative message allowed when bounded contract restoration was
  explicitly selected for that complete P/G cycle.
- Each implementor verifies the repository, checkout, branch, worktree, scope,
  and safety preconditions; performs only its assigned P step; returns a
  structured handoff; and stops before the matching G gate. A prompt grants no
  standing authority for a later P step, gate, closeout action, or replacement
  task.
- The supervisor independently evaluates every `Gnn`, records `pass`,
  `fail/correction`, or `pause/amend`, and does not delegate a gate decision to
  an implementor. The next P step remains unauthorized until the prior gate
  passes and its exact task action is approved.
- P01 through P06 use the bounded implementor/supervisor cadence. P07 and P08
  retain their phase numbers and matching gates for migration traceability but
  are supervisor-owned release-closeout phases, not implementor prompts.
- The supervisor owns plan amendments, corrections, commits, PR and merge
  decisions, operational cutover, user-soak handling, acceptance decisions,
  tagging, and release closeout. Every consequential action is separately
  previewed and explicitly approved; authorization for one action never
  implies authorization for the next.
- Amend this plan only if the requested architecture, directory ownership, or
  release boundary changes materially.
- Keep the implementation copy, existing project repository, external
  workspace, and all associated remotes private throughout `5.0.0`.
- Treat the existing private GitHub repository as the release authority and
  this original checkout as the operational acceptance environment.
- Do not create or push `v5.0.0` until the user explicitly accepts the live
  cutover.

### Supervision Modes

The exact launch or later-phase preview selects one mode for each complete P/G
cycle: **observation only**, **approval-gated attention**, or **bounded contract
restoration**. The choice does not carry into a later phase or replacement task.
Observation only never sends an implementor message. Approval-gated attention
requires a verified destination, exact message preview, and fresh approval for
every message. Bounded contract restoration permits at most one
non-replenishing message that directly and unambiguously restores an existing
approved contract; it cannot broaden scope, change requirements, grant
authority, or authorize destructive, external, or private-state work.

The active
[`agentic-feature-workflow` contract](../../skills/agentic-feature-workflow/SKILL.md)
and its orchestration reference define the portable evidence and authority
baseline. This migration may classify private-value exposure, unsafe database
copying, wrong-checkout mutation, premature remote action, rollback loss, or
live-state leakage as stricter attention signals and may narrow bounded
restoration to a hold or verbatim restatement of an existing criterion. It may
not weaken the active contract. Ambiguity, recovery direction, a second
message, or any permission change requires an exact preview and fresh approval.

```text
    fast-forwarded to 5.0.0 and used for live operational acceptance.

/Users/mperkhou/dev/codex/linkedin-career-mcp-public-exp/

/Users/mperkhou/dev/codex/linkedin-career-mcp-workspace/
    Durable external private workspace used first for parity validation and
    then as the live operational workspace.
```

Both destination paths must be absent before P01 starts. Never overwrite or
merge into a pre-existing directory under this plan.

## Workspace Contract

The migration checkout owns source code, templates, tests, skills, and public
documentation. The selected external workspace owns operational and private
state:

```text
<workspace>/
├── .env
├── .blacklist
├── profile/
│   ├── MASTER-RESUME.yml
│   └── MP-MASTER-RESUME.txt
├── output/
│   └── tracking/
│       └── applications.sqlite3
├── downloads/
└── tmp/
```

The ignored checkout `.env` is bootstrap-only. It may select:

```dotenv
LINKEDIN_CAREER_MCP_WORKSPACE=../linkedin-career-mcp-workspace
LINKEDIN_CAREER_MCP_PRIVATE_ENV_FILE=../linkedin-career-mcp-workspace/.env
```

It must not contain credentials or personal runtime settings.

Configuration precedence is:

1. Explicit CLI or Make override.
2. Process environment.
3. Selected private workspace `.env`.
4. Application defaults.

Existing explicit member flags remain supported. When no workspace is
configured, checkout-relative paths retain their current behavior during the
private migration. Makefile defaults must not silently override values loaded
from the process or private environment.

## Invariants

- The operational source checkout remains unchanged through G06. P07 may
  change it only by preserving its pre-cutover state, switching to `main`,
  fast-forwarding from the existing private remote, and adding ignored
  bootstrap configuration.
- The migration copy includes the source checkout's current tracked and
  uncommitted working-tree changes.
- The live source database is never copied with an unsafe file copy while it
  may be open; use SQLite backup semantics.
- Private environment values, application content, resume content, and job
  details do not appear in logs, reports, committed tests, or documentation.
- Templates and application code remain in the migration checkout.
- Models, prompts, timeout defaults, retry defaults, schema behavior, selected
  resume behavior, and workflow ordering do not change in this release.
- No external model, Codex, job-provider, or employer-facing call is required
  through the automated release-candidate and cutover gates. Normal live app
  use during the user-controlled soak may exercise the existing external
  workflows.
- No remote action occurs before P07, and no release tag is created before the
  user accepts the live cutover in P08.
- Every `5.x` migration release follows the same implementation-copy, private
  PR, operational-main cutover, live-soak, and explicit-acceptance cycle.
- Career Agent Workbench may be consulted as an architectural reference, but
  its workflow controller, configuration framework, and procedural machinery
  are not copied wholesale.

## P01 - Create Parallel Code And Workspace Copies

- Confirm both destination directories are absent.
- Record the source checkout's branch, commit, status, tracked diff, and a
  content-free inventory of ignored runtime members.
- Copy the repository, including `.git`, tracked files, current working-tree
  changes, and relevant untracked source files, into
  `linkedin-career-mcp-public-exp`.
- Exclude `.venv`, `output`, `tmp`, `downloads`, and the private `.env` from the
  code copy.
- Create `linkedin-career-mcp-workspace` with the current profile,
  `.blacklist`, output, downloads, tmp, and private `.env`.
- Create the destination SQLite database with SQLite's online backup facility.
- Keep the workspace `.env` a regular user-only file with mode `0600` on POSIX.
- Do not print environment values or private record content.

## G01 - Copy Integrity Gate

Pass only when:

- the operational source status and content hashes are unchanged;
- the migration copy reproduces the source's tracked and uncommitted code
  state;
- the workspace database passes `PRAGMA quick_check` and has the same
  content-free table and row counts as the source database;
- private runtime files exist only in the source and workspace copy; and
- neither destination was created by overwriting an existing path.

## P02 - Establish A Private Baseline

- In the migration copy, create branch
  `codex/public-rebuild-phase-1-workspace`.
- Build a new local `.venv`; do not copy the source environment.
- Run `git diff --check`, `make lint`, and `make test` before architectural
  edits.
- Inspect and identify every inherited working-tree change.
- If validation passes, prepare the inherited changes for one private baseline
  commit that preserves them independently from workspace implementation, but
  do not stage or commit them in the implementor task.
- Do not stage generated state or private workspace files.

## G02 - Baseline Gate

Pass only when the inherited code state is understood, the complete baseline
validation is green, the source checkout remains unchanged, and the supervisor
has independently reviewed the prepared diff. After an exact commit preview and
fresh user approval, the supervisor creates the private baseline commit and
verifies that the migration worktree is clean. Pause for user review if the
copied baseline itself is failing; the approval to create this commit grants no
authority for P03 or any remote action.

## P03 - Implement The Workspace Core

- Add a small immutable workspace-path model and one configuration loader in
  the existing configuration module.
- Support `LINKEDIN_CAREER_MCP_WORKSPACE` and
  `LINKEDIN_CAREER_MCP_PRIVATE_ENV_FILE`.
- Load only selectors from the ignored checkout bootstrap `.env`.
- Resolve conventional workspace members from the selected root.
- Load application settings from the private environment without printing
  values or mutating unrelated process state.
- Preserve existing defaults when no workspace is selected.
- Preserve explicit member-path overrides.
- Add focused tests for relative and absolute roots, precedence, conventional
  members, explicit overrides, malformed selectors, missing members, bootstrap
  restrictions, and sanitized errors.
- Bump the private migration release to `5.0.0` and align `pyproject.toml`, the
  top `CHANGELOG.md` entry, and `docs/release-notes/5.0.0.md`.

## G03 - Configuration Contract Gate

Pass only when focused configuration tests prove the documented precedence,
the bootstrap `.env` contains no private values, legacy checkout-relative
behavior remains covered, repr/error output is content-free, release metadata
is aligned, and no workflow behavior has changed.

## P04 - Integrate Stateful Command Surfaces

Thread the resolved workspace through:

- Make targets;
- job matching and seeding;
- JOD auditing;
- ARO and resume-generation scripts;
- v2 refinement;
- manual pass and highlighting;
- draft-to-ARO synchronization;
- resume rendering;
- MCP tools and workflows that read profile or application state; and
- Flask launch, downloads, and editor routes.

Requirements:

- Add a Make `WORKSPACE` selector and pass it only where needed.
- Do not let Makefile file defaults override process/private-environment model,
  timeout, retry, or Codex settings.
- Existing explicit database, output, profile, resume, and template flags
  remain higher-priority compatibility inputs.
- Stateful CLIs resolve defaults after parsing the workspace selector rather
  than binding checkout paths as argparse defaults.
- Stateless help and version commands do not require a workspace.
- Add command-composition and integration tests for every affected surface.

## G04 - Command Routing Gate

Pass only when every stateful direct CLI and Make target resolves the same
external workspace, explicit member overrides still win, stateless commands
remain usable without a workspace, and tests prove no state is written into the
code checkout while an external workspace is selected.

## P05 - Preserve Flask Background Workspace Ownership

- Ensure a Flask instance launched against a workspace retains that exact
  workspace for all background Make and script invocations.
- Ensure add, v1, v2, manual, highlighting, synchronization, editing,
  downloading, and deletion paths use the same resolved database and output
  root.
- Do not rely solely on the child process's current working directory.
- Preserve current action ordering, timeout/retry values, selected variants,
  and status behavior.
- Add Flask and background-command tests that use two isolated workspaces and
  prove commands cannot cross between them.

## G05 - Tracker Ownership Gate

Pass only when tracker tests prove that foreground and background operations
remain pinned to the selected workspace, a second workspace stays untouched,
and the code checkout receives no generated application state.

## P06 - Private Release-Candidate Validation

- Configure the migration checkout's ignored bootstrap `.env` to select
  `linkedin-career-mcp-workspace` and its private `.env`.
- Run `git diff --check`, focused workspace tests, `make lint`, and `make test`.
- Launch the Flask tracker against the external workspace and perform a
  read-only UI smoke test.
- Compare content-free schema versions, table counts, row counts, variant
  counts, selected-variant counts, and artifact availability with the G01
  baseline.
- Use disposable synthetic test fixtures for mutation-routing checks; do not
  mutate the source checkout or invoke a live model.
- Verify profile, database, output, download, and tmp paths all resolve beneath
  the external workspace.
- Update README and architecture documentation only enough to describe the new
  workspace contract and private migration setup.
- Return the scoped implementation, validation output, and sanitized parity
  evidence to the supervisor without staging, committing, or pushing.

## G06 - Release-Candidate Gate

The `5.0.0` candidate is ready for a private PR only when:

- all validation is green;
- the migration checkout is clean;
- the operational source checkout is unchanged;
- the external private workspace remains valid;
- Flask and every stateful command operate against the external workspace;
- the code checkout remains free of generated operational state when the
  workspace is selected;
- no live external call occurred; and
- changed files, commits, validation commands, and sanitized parity evidence
  are reported for user review.

After the implementor handoff, the supervisor independently reruns this gate.
If the candidate passes, the supervisor prepares an exact commit preview and
obtains fresh approval before creating the scoped `5.0.0` implementation
commit. The gate passes only after that commit is verified and the migration
checkout is clean. Commit approval grants no push, PR, merge, cutover, or later
phase authority.

G06 does not make `5.0.0` complete. It authorizes P07 only after the user asks
to proceed with the private PR and operational cutover.

## P07 - Supervisor-Owned Private PR, Merge, And Operational Cutover

P07 is a supervisor-owned release-closeout phase, not an implementor prompt.
The supervisor must preview the exact push, PR, merge, operational-checkout,
bootstrap-configuration, and Flask-launch actions and obtain approval at the
required granularity. Approval of one action does not authorize the next.

- Confirm that no Flask process or resume workflow is still using the
  checkout-local state before cutover.
- From the implementation copy, review the branch, diff, release metadata, and
  validation evidence; push the branch to the existing private `origin`; open
  a PR; wait for required checks; and merge it into the existing repository's
  `main`. Do not create the release tag yet.
- Record the merged `main` commit and preserve a content-free rollback record.
- In `/Users/mperkhou/dev/codex/linkedin-career-mcp`, record the current branch,
  commit, and status. If the worktree is not clean, preserve tracked and
  untracked changes in a named pre-cutover stash; do not drop that stash during
  `5.0.0`.
- Switch this operational checkout to `main` and update it with a fast-forward
  pull from the existing private remote. Verify that it is on the merged
  `5.0.0` commit with a clean tracked and untracked worktree.
- Verify the external workspace's private `.env` before replacing the ignored
  checkout `.env` with bootstrap-only workspace selectors. Preserve the old
  private checkout environment securely until the cutover is accepted, and do
  not print its values.
- Launch the Flask tracker from this operational checkout against
  `/Users/mperkhou/dev/codex/linkedin-career-mcp-workspace`, retain a durable
  content-free launch log, and perform a read-only UI and path-resolution smoke
  test.
- Verify that profile, database, output, download, and tmp paths resolve under
  the external workspace and that the old checkout-local runtime state was not
  modified by the smoke test.
- Report the local app URL, merged commit, clean-main status, resolved workspace
  root, rollback references, and sanitized smoke evidence. Leave the app ready
  for the user's normal work.

## G07 - Live-Soak Entry Gate

Pass only when the private PR is merged with green checks, this operational
checkout is clean `main` at the merged commit, the app launches from this
checkout against the external workspace, and no state leaks back into the code
checkout.

G07 pauses for the user to spend time using the live app and applying for jobs.
Do not infer acceptance from a successful smoke test and do not create or push
`v5.0.0`. If the user finds a defect, the supervisor prepares a bounded
correction phase on a new private branch from the merged candidate, obtains
exact approval, dispatches it to an implementor, independently gates it, and
then separately obtains approval to merge the correction under the
still-unreleased `5.0.0` metadata. Afterward the supervisor fast-forwards this
checkout again and repeats G07.

The live user soak is user-controlled and observed by the supervisor. It is not
delegated to an implementor and does not itself grant acceptance, correction,
tagging, or release authority.

## P08 - Supervisor-Owned User Acceptance And Release Closeout

P08 is a supervisor-owned release-closeout phase, not an implementor prompt.
The user's acceptance decision cannot be inferred or delegated. After explicit
acceptance, the supervisor separately previews the tag creation, tag push, and
remote verification actions and obtains approval before performing them.

- Begin only after the user explicitly confirms that the live `5.0.0` cutover
  succeeded.
- Collect content-free evidence that live writes occurred in the external
  workspace and did not occur in checkout-local operational paths.
- Confirm this operational checkout remains clean `main` at the accepted
  commit and the external workspace remains the selected private state owner.
- Create annotated tag `v5.0.0` on the accepted `main` commit with subject
  `Release v5.0.0` and a short body matching the changelog summary.
- Push `v5.0.0` to `origin` and verify it with
  `git ls-remote --tags origin refs/tags/v5.0.0`.
- Preserve the pre-cutover stash and secure rollback material unless the user
  separately authorizes their removal.

## G08 - Phase 1 Acceptance Gate

`5.0.0` is complete only when the user has explicitly accepted normal live app
operation, the external workspace owns all active private state, the
operational checkout is clean and synced, and the verified remote `v5.0.0` tag
points to the accepted commit.

## Supervisor Dispatch And Closeout Sequence

This section is a sequencing index, not a collection of standing prompts. At
each transition, the supervisor reconciles the real repository and migration
state, prepares a complete prompt for exactly one bounded P step, previews the
exact task action and supervision mode, and waits for fresh approval.

| Sequence | Owner | Authority boundary |
| --- | --- | --- |
| `P01 -> G01` | One implementor, then supervisor | Create the parallel copy and workspace only after exact P01 approval; the implementor stops before the supervisor's copy-integrity gate. |
| `P02 -> G02` | One implementor, then supervisor | Prepare and validate the private baseline; only the supervisor may approve and create the baseline commit while evaluating G02. |
| `P03 -> G03` | One implementor, then supervisor | Implement only the workspace core and release metadata, then stop before the configuration-contract gate. |
| `P04 -> G04` | One implementor, then supervisor | Integrate stateful command surfaces, then stop before the command-routing gate. |
| `P05 -> G05` | One implementor, then supervisor | Preserve Flask background workspace ownership, then stop before the tracker-ownership gate. |
| `P06 -> G06` | One implementor, then supervisor | Validate the candidate and return evidence without committing; only the supervisor may approve and create the candidate commit while evaluating G06. |
| `P07 -> G07` | Supervisor only | Separately approve and perform private PR/merge and operational cutover actions, then independently evaluate live-soak entry. |
| User soak | User, observed by supervisor | Normal job-application use supplies evidence but never implied acceptance or later authority. |
| `P08 -> G08` | Supervisor only | Begin only after explicit acceptance; separately approve tag creation/push, verify the remote tag, and evaluate final acceptance. |

No row authorizes a later row. An implementor never evaluates a gate, combines
multiple P steps, performs release closeout, launches another task, or receives
standing authority from an earlier prompt.

## Pause Conditions

Pause immediately when:

- either destination directory already exists before P01;
- any command before P07 would modify the operational source checkout;
- a private value or record appears in output intended for retention;
- the copied baseline fails before workspace implementation;
- the architecture requires changing model, prompt, retry, schema, resume, or
  selection behavior;
- a command cannot preserve one workspace across Flask background execution;
- an automated gate before the user-controlled soak would require a live
  external call;
- validation shows state written into the migration code checkout; or
- a remote action is proposed before P07;
- the PR cannot merge cleanly into the existing private repository;
- the operational checkout cannot be preserved and fast-forwarded safely;
- the private workspace environment cannot be verified before replacing the
  ignored checkout environment; or
- the user has not explicitly accepted the live cutover before P08.
