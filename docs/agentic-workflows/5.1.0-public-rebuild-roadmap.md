## Planning And Supervision Contract

The planning task becomes the supervisor for `5.1.0` and each later private
`5.x` migration release. It drafts and maintains one living Markdown plan,
dispatches exactly one bounded P step at a time to one separate user-owned
implementor task, and independently evaluates the matching G gate before
preparing any correction or later phase. An implementor never evaluates a gate,
receives multiple P steps, or gains standing authority from an earlier prompt.

Every task creation, later P-step send, correction, and replacement requires an
exact preview and fresh approval except for the single narrowly restorative
message available when bounded contract restoration was explicitly selected
for that complete P/G cycle. The exact preview selects **observation only**,
**approval-gated attention**, or **bounded contract restoration** for that cycle;
the mode and any message budget do not carry forward.

Migration plans may treat private-value exposure, unsafe database handling,
wrong-checkout mutation, premature publication or remote action, rollback loss,
and operational-state leakage as stricter attention signals. They may narrow
bounded restoration to a hold or verbatim restatement of an approved criterion,
but may not weaken the active `agentic-feature-workflow` evidence, approval,
role-separation, or authority contract.

## Release Cadence

Every private `5.x` migration release must remain centered on the existing
`mperkhou/linkedin-career-mcp` project repository and follow the operational
acceptance cycle established by `5.0.0`:

1. The supervisor starts from synced `main` and dispatches one bounded
   implementation step at a time for a candidate branch in the private parallel
   implementation checkout, with an independent gate after each step.
2. Implementors validate their bounded work without mutating the operational
   checkout; the supervisor independently verifies the candidate and owns any
   approved commit.
3. After separate exact approvals, the supervisor pushes the branch to the
   existing private remote, merges it through a reviewed PR with green checks,
   and withholds the release tag.
4. After separate cutover approval, the supervisor fast-forwards
   `/Users/mperkhou/dev/codex/linkedin-career-mcp` to clean `main` and runs the
   live app from that checkout against the durable external private workspace.
5. The supervisor pauses while the user performs normal job-application work
   and explicitly accepts or rejects the cutover; successful smoke checks never
   imply acceptance.
6. If needed, the supervisor plans and dispatches a bounded correction, gates
   it independently, and repeats the approved cutover. Only after explicit
   acceptance and separate tag-action approval does the supervisor create and
   push the release tag.

PR, merge, operational cutover, user-soak handling, acceptance, and tagging are
supervisor-owned closeout decisions outside implementor authority. Approval of
one action never authorizes the next.

The parallel checkout is an implementation surface, not a replacement
repository. The original checkout remains the operational acceptance surface
until the later history-free public-clone cutover is deliberately planned and
completed.

## Later Phases

**Synthetic substitution:** Replace tracked profile files with the Career Agent
Workbench demo profile, adapt its schema where necessary, move the synthetic
JOD into `docs/demo/`, and add an idempotent command that initializes an ignored
empty DB with only that job.

**Synthetic live workflow:** Run the seeded job through live v1, v2, regular
manual pass, and manual highlighting. Preserve sanitized logs, selected
variants, and rendered artifacts.

**Documentation rebuild:** Recreate README narratives, diagrams, tracker
screenshots, examples, architecture docs, ADRs, skills, and release
documentation using only synthetic state.

**PII and secret audit:** Scan text, binaries, screenshots, SVG metadata,
fixtures, absolute paths, emails, names, employers, and configuration. Establish
a small explicit allowlist for intended public identifiers.

**Fresh public 1.0.0:** Export the sanitized tree without `.git`, reset release
history to `1.0.0`, install and test from scratch, initialize a new repository,
and publish only after the final privacy gate.

**Public-clone cutover:** Rename the accepted operational source checkout to
`linkedin-career-mcp-bkp`, clone the new history-free public repository as
`linkedin-career-mcp`, and point its ignored bootstrap configuration to the
durable external private workspace established in `5.0.0`. Treat the backup as
rollback evidence, not as the active workspace, and verify the new checkout
before any private-state mutation.

**Rename experiment:** Once the new checkout works reliably against the backup
workspace, make another parallel copy and plan the package/project rename
independently.
